> 与 `AGENTS.md`、`openspec/config.yaml` 同源，不冲突时以本文件为最详细依据；如需推翻本文任何一条，MUST 先立一个 OpenSpec change 并经人类签字。

# 项目愿景与 MVP 边界（立项调研）

> 本节是 WanderChina 的"为什么"层，先于技术基准。定位为**面向外国游客**的"旅游社区 + 结构化攻略 + AI 实时助手"平台。数据截至 2025 全年（来源：travelchinaguide.com、english.www.gov.cn、en.nia.gov.cn、thinkchina.sg）。技术栈 MUST 为 **Vue 3 + Spring Boot + MySQL + Spring AI Alibaba**（见 §1，不可推翻）。

## 0.1 市场机会：需求真实且规模巨大

**结论：真实、高速增长、由政策直接驱动的增量市场，GO。**

- **2025 入境 1.545 亿人次（+17.1%），其中外国游客 3517 万**；入境总消费 **1311 亿美元（+39.2%）**——消费增速远超人次增速，说明人均客单在提升。
- **免签是核心引擎：2025 免签入境外国游客 3008 万，占全部外国游客的 73.1%（同比 +49.5%）**；免签国已扩至 **77 国**，另有 **240 小时过境免签覆盖 55 国 / 65 个口岸**。
- **地理下沉**：入境目的地正从北/上/广/深向**四五线城市扩散，年均增速高达 134%，重庆 +170%**。这恰是**英文信息与实操指引最稀缺**的地方——本平台价值随之下沉放大。
- 主要客源：韩国、泰国、新加坡、马来西亚、日本（均在免签网络内）；俄语区、意大利、澳洲等长线市场爆发（俄国游客赴沪月均增速 >80%）。

> 判断：这不是"造需求"，而是**政策红利把 3000 万+/年、且不懂中文、不带中国手机号的增量人群一次性推向市场**，而现有产品未按外国游客的实操需求重组信息。需求真实、规模足够、时机正当。

## 0.2 痛点地图（按严重程度排序）

| # | 痛点 | 严重度 | 说明与证据 |
| --- | --- | --- | --- |
| 1 | **移动支付** | 🔴 最高（阻断基本交易） | 中国移动支付渗透率约 73%，Alipay/WeChat 近乎强制；外国卡绑定、实名验证、额度限制长期被官方点名整改（thinkchina / gov.cn 指南）。落地即卡住 |
| 2 | **App 割裂 + 实名预约** | 🔴 高 | 火车票(12306)、景点门票(微信小程序实名预约)、打车(Didi)、酒店各自一套**中文 + 需中国手机/护照验证**的流程；外国游客难以完成 |
| 3 | **语言屏障** | 🟠 高（渗透一切） | 北/上/广之外英文标识、菜单、客服、App 极度稀缺；下沉城市（0.1 的 134% 增长区）几乎无英文支持 |
| 4 | **信息不对称与不可信** | 🟠 中高 | 实用信息碎片化、过时、多为中文；难形成**可信、结构化、可执行**的行程与实操答案 |
| 5 | **网络/连接** | 🟡 中 | Google/WhatsApp/Instagram 被墙，需提前配 eSIM/VPN；影响行中实时求助 |

**洞察：前 4 个痛点本质都是"实操/协调"问题，而非"内容不够美"问题——这正是 AI 实时助手 + 结构化攻略能直接命中、且传统内容平台没做透的地方。**

## 0.3 竞品分析：为什么现有产品没解决

| 产品 | 强项 | 为什么没解决外国游客实操痛点 |
| --- | --- | --- |
| **TripAdvisor / Lonely Planet / TravelChinaGuide** | 英文、评价库、静态攻略 | 内容**英文但浅、易过时**，偏"去哪儿看"而非"今天我怎么付款/买票/坐车"；无实时问答、无中国本地实操层、下沉城市覆盖弱 |
| **小红书** | **最新最真实**的实操干货（付款攻略、城市攻略） | **全中文 + 仅 App + 信息流不可结构化检索**；外国游客看不懂、筛不出、难验证，甚至需专门教程才敢用；UGC 无法直接变进行程 |
| **马蜂窝** | 结构化自由行攻略成熟 | **服务国内/出境中国用户，中文only**，受众根本不是入境外国游客；近年声量下滑 |

**共同空白（=机会）：没有任何产品同时做到 (a) 英文原生 (b) 结构化且保鲜 (c) 面向"付款/App/订票"的实时问答助手 (d) 外国游客社区。** 根因：这些玩家要么"英文但浅"、要么"深但中文"；而免签带来的 3000 万+/年新人群是**近期才爆发的增量**， incumbents 的产品为本地用户/广告变现而设计，服务这个入境细分既非其优先级、也缺对应 UX。

## 0.4 切入建议与 GO/NO-GO

**最值得切入的方向：以"AI 实时助手 + 结构化景点攻略"为楔子，服务英文用户下沉免签游的实操痛点；社区作为后置增长飞轮，不作冷启动主攻。**

理由：
- **痛点频次最高、最可变现的是"实操求助"**（付款/App/订票/交通），这恰是 AI 助手能规模化解答、而 incumbents 靠人工内容难保鲜的地方。
- **社区冷启动是鸡生蛋难题**，且 TripAdvisor/小红书已占 UGC；用"助手 + 结构化攻略"先单点建立信任与留存，再长社区，路径更稳。
- **AI 助手对"中国实时事实"要求高准确率**（答错车次/签证/付款=真实伤害），因此助手 MUST 建立在**人工维护的结构化知识库**之上（= 景点/攻略数据模型），而非裸大模型——**这层结构化数据本身就是竞品难复制的数据护城河**。

**GO/NO-GO：GO。** 支撑：政策驱动的 3000 万+/年且高增速的 underserved 人群（0.1）＋前四痛点是同一类"实操/协调"缺口（0.2）＋现有玩家结构性错位（0.3）＋可用锁定栈 Vue3+SpringBoot+MySQL 落地的清晰楔子（0.4）。

**必须正视的风险（诚实边界）：**
1. **不碰支付本身**：付款趋势正被 Alipay TourCard/绑外卡解决，平台只做**信息/协调层**，不做资金/支付（无牌照即违规）。
2. **AI 准确性是生命线**：助手须挂知识库＋事实校验，禁止幻觉直接对外。
3. **内容保鲜是运营成本**：结构化攻略需持续人工/半自动维护，否则重蹈 TripAdvisor 过时问题。
4. **SEO 架构张力**：面向外国用户的公开内容平台高度依赖搜索获取——这与 §1 锁定的 SPA 栈有张力；**MUST 按 §2 的"SEO 例外"用 Vite 预渲染/SSG，或单独立 change 评估**，禁止为 SEO 顺手改用 Next/Nuxt。
5. **中国境内合规**：社区/UGC 涉及 ICP 备案、实名制、内容审核；首个社区功能上线前 MUST 在独立 change 中定合规方案。

## 0.5 MVP 边界与核心模块优先级

**MVP 主张：** 让一个外国游客能**看懂去哪、如何实操、并被实时答疑**；先把"答案 + 行动"闭环跑通，社区与交易后置。

**模块全景（6 个，按优先级）：**

| # | 模块 | 优先级 | 状态 | 依据与数据模型提示 |
| --- | --- | --- | --- | --- |
| 1 | **首页 / 发现** | **P0** | Hero 区已完成（`homepage-hero`），发现流待建 | 内容外壳与分发入口；聚合"热门景点/热门帖子"卡片；数据表遵循 §6 |

## 2. 选型结论与复盘

**结论：坚持现有 Vue 3 + Vite + TS + Element Plus（SPA）+ Spring Boot 3，不采用 Nuxt 3 或 Next.js。**

决策依据（团队约束：全员有 Vue 3 基础、无 React 经验；长期运营平台；AI 辅助开发、追求 AI 生成质量最高）。四维度 5 分制打分：

| 维度 | Vue 3 SPA（现状） | Nuxt 3 | Next.js |
| --- | --- | --- | --- |
| 团队学习成本 | 5 | 4 | 2 |
| AI 生成质量（本架构下） | 5 | 3 | 3 |
| 生态成熟度 | 4 | 4 | 5 |
| 长期维护性（长跑 + Java 后端） | 5 | 3 | 3 |
| **合计（/20）** | **19** | 14 | 13 |

理由要点：
- **学习成本**：团队既有技能直接复用；Next.js 需从零学 React。
- **AI 生成质量**：在"独立 Java 后端 + 分离前端"架构下，纯 SPA 只有单一渲染模型、无 hydration 心智负担，AI 产出最稳定；Nuxt/Next 会再叠一层 Node SSR/RSC，AI 常生成过时或错配写法，且与 Spring Boot 形成"双服务端"概念冲突。
- **生态**：Element Plus 在国内企业级 Vue 生态成熟度高，契合旅游平台后台与中文场景。
- **长期维护**：SPA 不引入额外 Node 运行时层，前后端边界干净、运维面最小，适合长期运营。

**唯一反例 = SEO**：面向搜索引擎的公开营销/落地页需要可抓取 HTML，是 SSR 元框架的本职。处置原则——
- 优先在 Vite 内用**预渲染 / SSG** 解决；
- 若确需运行时 SSR，**MUST 单独立 OpenSpec change 评估**（例如引入 Nuxt 的局部方案）；
- **禁止**在业务开发中"顺手"更换框架或引入第二个渲染服务。

## 3. 禁止动作（不可违反）

- ❌ **禁止引入 React / Next.js / Angular**（含任何相关代码、依赖、模式）。（后果：与锁定 Vue 3 栈严重冲突，编译/运行崩溃，且团队无 React 能力。）
- ❌ **禁止引入 Tailwind CSS / MUI / Ant Design（antd / ant-design-vue）等其它 UI 或原子化 CSS 方案**；UI 一律 Element Plus，样式一律 SCSS scoped。
- ❌ **禁止在未经批准的 change 下引入 SSR/SSG 元框架（Nuxt/Next）或第二套服务端渲染层。**
- ❌ **禁止在 Controller 编写业务逻辑或直接访问 Repository**，必须严格 `Controller -> Service -> Repository` 三层。
- ❌ **禁止绕过 OpenSpec 流程直接改业务代码**；任何代码改动先产出 proposal/design/tasks，人类签字后动手。
- ❌ **禁止绕过 TDD**：实现前先写失败测试（RED -> GREEN -> REFACTOR）。
- ❌ **禁止以"AI 生成质量更高"为单一理由推翻已锁定栈**（该主张已在第 2 节量化复盘，结论相反）。
- ❌ **禁止做没要求的事 / 预防性抽象**（YAGNI、DRY）。
- ❌ **禁止 AI 能力翻墙直连境外模型（OpenAI 等）**；AI 一律经 **Spring AI Alibaba** 走阿里云百炼 / 通义千问。且 AI 助手 MUST 挂人工知识库 + 事实校验，禁止裸模型/幻觉直接对外（红线 2）。

## 4. 允许 / 推荐模式

- 前端统一 `<script setup lang="ts">` Composition API；请求收敛到 `src/api/`，组件不裸调 axios。
- UI 组件用 Element Plus；自定义样式用 SCSS scoped。
- 后端统一响应 `Result<T>{ code(0=成功) / message / data }` + `@RestControllerAdvice` 全局异常（不回显堆栈）。
- 接口契约由 springdoc 生成（dev/test），前端类型与之对齐。
- 跨端通信走 `/api` + dev proxy；prod 关闭 OpenAPI 文档。

修改本基准的唯一合法路径：新建 OpenSpec change（`openspec/changes/<name>/`）→ `proposal.md` 论证为何要偏离本文件 → 人类签字 → 实施 → 归档并同步本文。

## 6. 数据库设计规范（Spring Boot 3 + JPA + MySQL 8 + Flyway）

> 后续所有建表、字段、索引、迁移 MUST 以此为准；违反视为缺陷。适用对象含"热门帖子""热门景点"等业务表。

### 6.1 主键策略

**结论：业务实体主键统一用 `BIGINT` + 雪花（Snowflake）ID；禁止随机 UUID 作主键。**

| 方案 | 结论 | 关键理由 |
| --- | --- | --- |
| 自增 `AUTO_INCREMENT` | 仅限纯内部关联表（junction）/ 无分布式需求 | 紧凑、聚簇友好，但顺序可枚举（记录数泄露 / IDOR），且难做分库分表与 ID 预生成 |
| 随机 `UUID(36)` | ❌ 禁作主键 | 随机写导致 InnoDB 页分裂、写放大；每条二级索引都冗余存 36 字节 PK |
| **雪花 `BIGINT`** | ✅ 业务表默认 | 时间有序≈追加写、无碎片；全局唯一，天然支持分布式/分表与先分配 ID 后落库；不外泄总量 |

强制约束：
- **API 边界必须把雪花 ID 序列化为 `String`**（BIGINT 超过 JS `2^53` 会丢精度）。JPA 侧保持 `Long`，DTO/JSON 用 `String`（`@JsonSerialize` 或全局 Long→String）。
- 需要对外不透明标识时，另设 `slug` / `public_id` 业务字段（可加 UNIQUE 索引），**主键仍是 BIGINT 雪花，二者分离**。
- 字符型 `VARCHAR` 主键仅作业务唯一键（如景点 code），走 UNIQUE 索引，不作为物理主键。
- 雪花 `workerId/datacenterId` 由配置注入，禁止各实例默认值冲突（多实例部署前必须分配）。

### 6.2 公共字段（每表必含）

统一由 JPA `@MappedSuperclass BaseEntity` 承载，业务 Entity 继承；Hibernate 物理命名策略映射为 snake_case。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `BIGINT` | PK, NOT NULL | 雪花 ID（见 6.1） |
| `created_at` | `DATETIME(3)` | NOT NULL | 创建时间，存 UTC（`@CreationTimestamp`） |
| `updated_at` | `DATETIME(3)` | NOT NULL | 更新时间，`@UpdateTimestamp` |
| `created_by` | `VARCHAR(64)` | NULL | 创建者标识；系统写入填 `'system'`，无上下文可空 |
| `updated_by` | `VARCHAR(64)` | NULL | 最后修改者标识 |
| `is_deleted` | `TINYINT(1)` | NOT NULL DEFAULT 0 | 逻辑删除标记（0=正常）；查询默认过滤 `=0` |
| `version` | `INT` | NOT NULL DEFAULT 0 | JPA `@Version` 乐观锁，防并发覆盖 |

约定：
- 时间统一 `DATETIME(3)` 存 UTC，**不用 `TIMESTAMP`**（避免隐式时区换算与 2038 边界）；时区在应用/前端边缘转换。
- 逻辑删除为默认策略；确需物理清理的数据在专门 change 里定夺。
- `deleted_at`（DATETIME NULL）可按需追加用于回收站/审计，非强制。

### 6.3 字段约束原则（NULL vs NOT NULL）

**默认 NOT NULL + 显式默认值；仅当"缺失本身是合法业务状态"才允许 NULL。**

- 必填业务属性：`NOT NULL`，并给合理默认（字符串 `''`、枚举码、数值 `0`）。
- 可选关系：用**可空外键**表达"暂无/未知"（如 `city_id NULL`）。
- 禁止用空串/0 与 NULL 混淆语义：一个字段只能有一种"无值"表达，写进注释。
- **唯一约束列必须 NOT NULL**：MySQL 唯一索引允许存在多个 NULL，会让唯一性形同虚设。
- 金额/度量：`DECIMAL(p,s) NOT NULL`，禁止 NULL、禁止用浮点表示钱。
- 聚合/比较注意 NULL：`COUNT(col)`、`!=`、`NOT IN` 会排除 NULL，统计口径须显式处理（配合 `is_deleted`）。
- 长文本/富文本内容允许 NULL（尚未填写），但标题等关键摘要 NOT NULL。
- 布尔/状态用 `TINYINT`/短码 + NOT NULL + 默认，不用 `BIT`/`ENUM` 隐式默认。

### 6.4 索引策略

**原则：为高频读路径而建，控制写放大；先 EXPLAIN 验证，再决定是否长期保留。**

- 该加索引：高频出现在 `WHERE` / `JOIN` / `ORDER BY` 且**区分度高（cardinality 大）**的列。
- 组合索引遵循**最左前缀**，列顺序：等值条件 → 范围条件 → 排序列；尽量做**覆盖索引**避免回表。
- **外键列必须显式建索引**：MySQL 不因 FK 自动建索引，Join 与约束校验都吃这个索引。
- 业务唯一键：建 `UNIQUE`（如 `slug`、`email`、景点 `code`）；配合 6.3 NOT NULL。
- 低基数列（`is_deleted`、状态、性别）**禁止单列索引**；只允许作为组合索引的前置过滤列（如 `idx(is_deleted, created_at)` 支撑"最新未删除"列表）。
- 写热点列谨慎索引：如浏览量/点赞数等高频更新计数列，避免为其单独建索引放大写成本；排序需求另设快照/统计方案。
- 前缀索引：超长 `VARCHAR`/`TEXT` 需索引时用前缀长度，勿整列。
- 搜索类（帖子标题/正文）走 MySQL `FULLTEXT`（或后续独立检索方案），不用 `LIKE '%x%'` 全表扫。
- 禁止在索引列上做函数/隐式类型转换（使索引失效）。
- 命名：普通 `idx_<table>_<cols>`，唯一 `uk_<table>_<cols>`；每表索引数量保持克制（建议 ≤5，除主键）。

### 6.5 Flyway 迁移纪律

- 一切 DDL/数据修正**只能通过 Flyway 版本化脚本**：`src/main/resources/db/migration/V{n}__{desc}.sql`；禁止手工改库、禁止 `ddl-auto=update/validate` 参与生产 schema。
- 脚本**只向前（forward-only）、合并后不可变**；已上线脚本不得修改，需纠正则新开一个版本。
- 每个业务 change 的建表/加列/加索引都随该 change 提交对应迁移。
- 迁移需可回滚演练（备份或配套 undo 流程在首个持久化 change 中定义）。
- 字符集/引擎统一：`utf8mb4` / `utf8mb4_general_ci`（或 `0900_ai_ci`）、InnoDB；本条在具体建表 change 中钉死。
